# Project #1: Applicant Tracking System

## Question 1

A class that inherits from forms.Form is `AddApplicantForm` located in `ats/forms.py:100`. The purpose of this form is to add an application for a specific candidate to a specific job opening. This form is accessed via the "Add Applicant" button on a job opening's page, which is found at `ats/templates/ats/job_detail.html:33`. The button links to the path defined in `ats/urls.py:23-26` which points to the `job_application_create` view in `ats/views.py:156`. The form has a live search box that offers only candidates who are eligible to apply for that job, as well as an application date field. The template for the application form itself is `ats/templates/ats/application_form.html`. This template loops over the fields, using the `candidate_picker.html` partial and HTMX/Javascript to enable the live candidate search box. Upon form submission, the view calls `form.is_valid()` before passing the valid data on to `submit_application` located at `ats/views.py:55`. `submit_application` then calls `create_application` in `ats/services.py:107` which writes to both the Application model as well as the StageChange model.

A class that inherits from forms.ModelForm is `CandidateForm (ats/forms.py:25)` which contains a `clean()` function which converts the email field into all lower case. This form is responsible for creating and editing Candidates and all of their information. The template for the form is located at `ats/templates/ats/candidate_form.html` and is displayed by two different views - both `candidate_create (ats/views.py:229)` and `candidate_edit (ats/views.py:252)` call `candidate_form_response (ats/views.py:33)` which does all the work. Once the form is submitted, the view calls `form.is_valid()` before passing the data to the `save_candidate (services.py:40)` service which writes the data to the model.

The important difference between these two forms is actually obscured by the way the agent decided to use services located in `ats/services.py` to handle any action that changes data. That being said, the `CandidateForm` form could have called `form.save()` itself and updated the Candidate database. This is due to the fact that it inherits from forms.ModelForm. Since the `AddApplicantForm` form actually needed to update two databases at the same time (the Application and the StageChange database), the agent chose to write that form as a standard forms.Form form which then passed the necessary data to the service which updated both databases. If the form had inherited from forms.ModelForm, it could have only run form.save() on a single database. The biggest difference between the two forms is that `CandidateForm` could write directly to the database, whereas `AddApplicantForm` could only collect form data and pass it along for further use.

## Question 2

An association table relationship exists between the `Candidate` model and the `JobOpening` model. These two models are connected via the explicitly defined `Application` model which has Foreign Keys to both the other models. In this particular case, a single foreign key would not be sufficient to fully map the relationship because each candidate can apply to many jobs and each job opening can have many applications from different candidates. To only have a single foreign key linking `Candidate` and `JobOpening` would restrict the relationship to a one-to-many on either side, depending on which model the foreign key resided in. The `Application` model is defined explicitly, since it needs to store other fields, such as the stage, application date, and created at fields. These fields apply only to the application itself and are not determined by the relationship between `Candidate` and `JobOpening`.

## Question 3

My UI prototype was created to determine the aesthetic of the main "Pipeline Board" page where applicants are tracked throughout the different stages for each job opening. The first two options were somewhat similar, with columns for each status and "cards" for each applicant. The cards displayed the applicant's name and email address. In the first option, each card contained a drop down box with a list of potential stages which that card could be moved into. The second option did not have the drop down box, but each card was actually able to be dragged and dropped into the new stage. The third option was very different - it displayed the applicants in a simple list. Each row of the list had much richer detail about each applicant than what was displayed on the cards in each of the first two options. I decided to go with the drag-and-drop cards from the second option, but combined it with the third option and had the agent add the richer detail to the cards themselves. This decision can be easily seen by viewing the pipeline board for a job opening in the actual application, but it also appears in the PRD at `prd/applicant-tracking-system.md:103-111`.

## Question 4

One code structure decision I made during the grill-me interview was to use a single app for the entire project. The agent's other two options were to write several different apps (accounts, jobopenings, candidates, etc.) or to split the project into just two apps (accounts, and the main app). I approved the option to write the project in a single app because I felt like the project was small enough to accomodate this, and also because of the interconnectedness of all of the features. The agent warned that writing multiple apps would lead to many circular imports and dependencies. I rejected the second option (two apps) because I felt it was not meaningfully different from the single app solution - the accounts app would have had very little code to it and the majority of the project would have still been in a single app. The agent attempted to structure the code as efficiently as possible within a single app - thus `ats/pipeline.py` holds the stage definitions and transition map, `ats/services.py` handles any operation that changes data, and the views in `ats/views.py` mainly call services and then render templates. I think that this choice and design structure fit the scope of this project, but I will say that it seems to have led to some oddities in the code. One example is the `CandidateForm` functionality I mentioned in Question 1 - the form is fully capable of writing to the database itself, but instead calls on a function from `services.py` simply to not break the rule about services handling database changes. Another side effect I noticed of using a single app is that the agent's context window filled much more quickly. Since my views are all contained in a single `views.py` file instead of split over multiple apps, each file the agent needed to read tended to be much longer - the agent would often be close to 100k tokens by the time we got through the TDD stage.
